## 1. Executive Summary

A comprehensive diagnostic audit was conducted across the entire hardware, backend, and frontend codebase of the **Cloud RISC-V Visual Simulator & Waveform Studio** to resolve four specific diagnostic questions:

1. **Why do register values remain zero after assembling, loading, and stepping/running a program?**
2. **Why do memory values remain zero even when the program contains active store instructions (`sw`)?**
3. **Why does the waveform viewer display only the clock signal?**
4. **Is the frontend displaying actual RTL simulation results, or is it decoupled and relying on a separate JavaScript emulator, static mock data, or fallback values?**

### Key Findings at a Glance

* **The Hardware RTL is 100% Functional:** The SystemVerilog RTL implementation (`pipeline_cpu.sv`, `regfile.sv`, `data_memory.sv`, `alu.sv`, `hazard_unit.sv`, `forwarding_unit.sv`) was subjected to 7 comprehensive verification testbenches (`verification/scripts/run_all.py`) comprising **130 hardware assertions**. All 130 assertions **PASSED** (100% pass rate). The RTL correctly executes arithmetic, load-use hazards, forwarding, taken/not-taken branches, stores, and edge cases.
* **The Root Cause of Zero Registers and Memory:** The React frontend is **completely decoupled** from the Verilator C++ simulation engine. The frontend state (`clientSim.registers`, `clientSim.memory`, `clientSim.pipeline`) is driven strictly by an independent, client-side JavaScript simulator (`simulatorEngine.js`). Although `App.jsx` issues an asynchronous HTTP request `await simulationService.step()` to the backend, **its return value is discarded**, and the API endpoint `/api/simulator/step` does not even return register file or data memory payloads. Furthermore, the frontend functions `fetchRegisters()` and `fetchMemory()` are **never called anywhere in the UI**. Even within the client-side JavaScript simulator, registers remain zero if instructions have not completed the 5-stage latency or if the user steps before clicking "Assemble & Load" (leaving `assembledProgram` empty).
* **The Root Cause of Waveforms Showing Only Clock:** In `WaveformStudio.jsx`, the default view is `'live'` (Live Logic Analyzer), which plots signal telemetry recorded by the client JavaScript simulator (`simulatorEngine.js`). When `assembledProgram` is empty or during the initial cycle, all pipeline stages are invalid (`valid = 0`), control lines are inactive, and ALU results are 0. The only signal that changes state is `clk: next.cycle % 2 === 0 ? 0 : 1`. In the separate Verilator VCD view, hardware traces generated by Verilator are written to `/home/pc/riscv-verilator-build/pipeline.vcd`, but are only fetched when tracing is explicitly stopped via "Stop Trace" — they are never streamed live.
* **Orphaned / Unused Files:** `backend/app/telemetry.py` is an empty file (0 bytes) and is never imported. `frontend/src/data/sampleVcd.js` contains a static sample VCD string; it is only loaded on explicit user click of "Load Sample VCD" and is not masquerading as real simulation data in the primary pipeline view.

## 2. Actual Project Architecture

The project was originally architected as a unified hardware-in-the-loop visualization system:
```text
[SystemVerilog RTL] ──▶ [Verilator C++] ──▶ [FastAPI Backend] ──▶ [React Frontend UI]
```

However, statutory inspection of the codebase reveals that the application actually contains **two completely independent, competing simulation engines running in parallel without data synchronization**:

```text
                               ┌─────────────────────────────────────────────────────────────┐
                               │                    FRONTEND BROWSER                         │
                               │                                                             │
  [Assembly Editor] ───────────┼────────────────────────────────────────┐                    │
         │                     │                                        │                    │
         │ (Assemble & Load)   │                                        ▼                    │
         │                     │                              [simulatorEngine.js]           │
         │                     │                         (Pure JavaScript RV32I Emulator)    │
         │                     │                                        │                    │
         │                     │                                        ▼                    │
         │                     │                                 [clientSim State]           │
         │                     │                           {registers, memory, pipeline,     │
         │                     │                                    waveforms}               │
         │                     │                                        │                    │
         │                     │         ┌──────────────────────────────┴───────────────┐    │
         │                     │         ▼                                              ▼    │
         │                     │ [RegisterFileInspector]                           [Waveform]│
         │                     │ [MemoryViewer]                                   (Live Mode)│
         │                     │ [PipelineFlowView]                                          │
         │                     └─────────────────────────────────────────────────────────────┘
         │
         │ HTTP POST /api/assembler/assemble-and-load
         ▼
┌────────────────────────────────────────────────────────────────────────────────────────────┐
│                               FASTAPI BACKEND (Python)                                     │
│                                                                                            │
│  main.py ──▶ assemble() ──▶ writes assembled.hex ──▶ simulator_manager.load_program()    │
│                                                                   │                        │
│  POST /api/simulator/step ─────────────────────────────────┐      │ (JSON-Lines / stdio)   │
│  (Response: {cycles, pipeline_state} ONLY; NO REGS/MEM)    │      ▼                        │
└────────────────────────────────────────────────────────────┼───────────────────────────────┘
                                                             │
                                                             ▼
┌────────────────────────────────────────────────────────────────────────────────────────────┐
│                        WSL2 / VERILATOR HARDWARE SIMULATION ENGINE                         │
│                                                                                            │
│   Vriscv_sim_top (C++ Wrapper) ──▶ riscv_sim_top.sv ──▶ pipeline_cpu.sv                   │
│   (Executes actual hardware clock cycles, updates registers and data memory)               │
│                                                                                            │
│   * State extraction available via:                                                        │
│     - SimulationEngine::readRegisters()  (RTL debug_reg_data)                              │
│     - SimulationEngine::readMemory()     (RTL debug_dmem_data)                             │
│     - SimulationEngine::startTrace()     (Verilator VCD dumper)                            │
│   * BUT THESE ENDPOINTS ARE NEVER CALLED BY THE FRONTEND UI TO UPDATE THE DISPLAY!         │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Architectural Findings:
1. **Frontend Disconnection:** The React UI renders exclusively from `clientSim`, which is managed entirely in JavaScript memory by `frontend/src/services/simulatorEngine.js`.
2. **Orphaned Hardware Engine:** The real Verilator RTL simulation engine runs in WSL2 via FastAPI, correctly executes machine cycles, and updates its internal hardware registers, but **none of this hardware state is ever mapped back to the user interface**.
3. **Incomplete Step Protocol:** Even if the frontend listened to `/api/simulator/step`, the backend endpoint only returns `{ "cycles": N, "pipeline_state": { ... } }`. It completely omits the register file (`registers`) and memory array (`memory`).

## 3. Complete Simulation Data-Flow Map

The complete execution chain from user keystrokes in the browser to the pixel rendering in the UI was traced step-by-step:

### Step 1: Assembly Code Input
* **Component:** `frontend/src/components/editor/AssemblyEditor.jsx` (Lines 30–50)
* **Action:** User types assembly text into the CodeMirror/monaco editor.
* **Handler:** `handleSourceChange(newSource)` in `frontend/src/App.jsx` (Line 233).
* **State Target:** `source` state in `App.jsx`.
* **Disconnection Point:** Updating `source` does **not** update `assembledProgram`. If the user types code and immediately clicks "Step" or "Run" without clicking "Assemble & Load", `assembledProgram` remains an empty array `[]`.

### Step 2: Assembly & Program Loading
* **Component:** `frontend/src/App.jsx` -> `handleAssembleAndLoad` (Lines 200–231).
* **Client Path:**
  1. Calls `assembleRV32I(source)` from `frontend/src/services/simulatorEngine.js` (Line 204).
  2. Sets `assembledProgram = instructions` (array of parsed JS objects).
  3. Resets `clientSim = createInitialState()`, zeroing out all 32 registers, all memory cells, cycle count to 0, and clearing the pipeline latches.
* **Backend Path:**
  1. Checks `if (backendConnected)` (Line 215).
  2. Calls `simulationService.start()` -> `POST /api/simulator/start`.
  3. Calls `simulationService.assembleAndLoad(source, 'assembled.hex')` -> `POST /api/assembler/assemble-and-load`.
  4. Calls `simulationService.reset()` -> `POST /api/simulator/reset`.
* **Backend Implementation:**
  1. `backend/app/main.py` (Line 175): `assemble_and_load_endpoint` invokes Python assembler `assemble(request.source)`.
  2. Converts instructions into 32-bit hex strings (e.g. `00500093`).
  3. Writes `assembled.hex` into `/mnt/d/RISC-V_Project/hardware/sim/assembled.hex` via `wsl.exe ... tee`.
  4. Calls `simulator_manager.load_program("assembled.hex")` in `backend/app/simulator.py`.
  5. Sends `{"command": "load_program", "program_file": "/mnt/d/RISC-V_Project/hardware/sim/assembled.hex"}` over stdin to the C++ process.
* **C++ Engine Implementation:**
  1. `hardware/sim/simulation_engine.cpp` -> `loadProgram()` calls `reconstructModel()`.
  2. `reconstructModel()` passes `+imem_file=/mnt/d/RISC-V_Project/hardware/sim/assembled.hex` to Verilator args.
  3. Reconstructs `top_ = std::make_unique<Vriscv_sim_top>(context_.get())`.
  4. Applies hardware reset (`top_->rst_n = 0`, clocks 1 cycle, then `top_->rst_n = 1`).
  5. In RTL (`hardware/rtl/instruction_memory.sv`), `$readmemh` reads `assembled.hex` into `rom`.

### Step 3: Simulation Stepping (`handleStep`)
* **Component:** `frontend/src/App.jsx` (Lines 126–138):
```javascript
const handleStep = useCallback(async () => {
  // 1. Advance client cycle-accurate simulator
  setClientSim(prev => simulateStep(prev, assembledProgram));

  // 2. If backend is connected, also step the RTL simulator asynchronously
  if (backendConnected) {
    try {
      await simulationService.step();
    } catch (e) {
      console.warn('Backend step sync error:', e.message);
    }
  }
}, [assembledProgram, backendConnected]);
```
* **Failure Analysis:**
  1. Notice that `simulateStep(prev, assembledProgram)` is executed synchronously in JavaScript.
  2. The backend call `await simulationService.step()` is invoked asynchronously, but **its return value is discarded**.
  3. The state returned by `simulationService.step()` contains:
     `{ "cycles": ..., "pipeline_state": { "fetch": ..., "decode": ..., "execute": ..., "memory": ..., "writeback": ... } }`.
  4. The returned `pipeline_state` is **never passed to `setClientSim` or any React state**.
  5. The returned payload from `POST /api/simulator/step` **does not include `registers` or `memory`**.

### Step 4: Register & Memory Extraction
* **Backend Capabilities:**
  * `GET /api/simulator/registers` in `backend/app/main.py` (Line 236) invokes `simulator_manager.read_registers()`, which commands C++ `{"command": "read_registers"}`. C++ queries `top_->debug_reg_data` across registers 0–31 and returns all 32 hardware register values.
  * `POST /api/simulator/memory` in `backend/app/main.py` (Line 244) invokes `simulator_manager.read_memory()`, which queries `top_->debug_dmem_data` across addresses and returns actual data memory values.
* **Frontend Failure Point:**
  * Searching all files in `frontend/src/` proves that **neither `fetchRegisters` nor `fetchMemory` is called anywhere in the UI**.
  * `RegisterFileInspector.jsx` receives `props.registers`, which is passed from `App.jsx` as:
    ```javascript
    registers={Array.from(clientSim.registers)}
    ```
  * `MemoryViewer.jsx` receives `props.memory`, which is passed from `App.jsx` as:
    ```javascript
    memory={memoryArray} // derived directly from clientSim.memory
    ```
  * Therefore, the register file and memory inspectors display **100% JavaScript emulator memory**, completely ignoring the hardware simulation in WSL2.

## 5. Register and Memory Data-Flow Investigation

### 5.1 C++ Simulation Engine & RTL Probing
In `hardware/sim/simulation_engine.cpp`:
* `readRegisters()` (Lines 232–246):
```cpp
json SimulationEngine::readRegisters() {
    json regs = json::array();
    for (uint32_t r = 0; r < 32; ++r) {
        top_->debug_reg_addr = r;
        top_->eval();
        regs.push_back(top_->debug_reg_data);
    }
    return {{"status", "ok"}, {"command", "read_registers"}, {"data", {{"registers", regs}}}};
}
```
* `readMemory()` (Lines 248–275):
```cpp
json SimulationEngine::readMemory(uint32_t start_addr, uint32_t count) {
    json mem = json::array();
    for (uint32_t i = 0; i < count; ++i) {
        uint32_t addr = start_addr + i * 4;
        top_->debug_dmem_addr = addr;
        top_->eval();
        mem.push_back({{"address", addr}, {"value", top_->debug_dmem_data}});
    }
    return {{"status", "ok"}, {"command", "read_memory"}, {"data", {{"memory", mem}}}};
}
```

## 8. Simulation Lifecycle and State Consistency

1. **Initial Mount:**
   * `App.jsx` initializes `clientSim` using `createInitialState()`.
   * All registers are 0x00000000. Data memory is empty.
   * `assembledProgram` is initialized to `[]` (empty array).
   * Backend link is checked via `simulationService.checkBackend()`.
2. **User Edits Source:**
   * User enters assembly instructions in the editor.
   * `handleSourceChange` updates `source`.
   * **State desynchronization:** `assembledProgram` is still `[]`.
3. **User Clicks "Step" or "Run" Without "Assemble & Load":**
   * `handleStep` executes `simulateStep(prev, assembledProgram)`.
   * Because `assembledProgram` is empty, the fetch stage reads no instructions.
   * The pipeline remains in "Not Started" / bubble state.
   * Registers remain 0. Memory remains 0. Waveform shows only CLK.
4. **User Clicks "Assemble & Load":**
   * Code is assembled in JavaScript: `setAssembledProgram(instructions)`.
   * Code is sent to backend: `assembleAndLoad(source, 'assembled.hex')`.
   * Backend writes hex, loads into `Vriscv_sim_top`, resets CPU.
   * `clientSim` is reset to cycle 0.
5. **User Steps After "Assemble & Load":**
   * `handleStep` calls `simulateStep(prev, assembledProgram)`.
   * The JavaScript simulator advances 1 cycle.
   * Cycles 1–4: Instruction moves through IF, ID, EX, MEM.
   * **During cycles 1–4, WB stage has not occurred, so registers remain 0.**
   * In cycle 5, the first instruction enters WB, and only then does the destination register update in `clientSim.registers`.
   * Meanwhile, `simulationService.step()` runs in WSL2, but its result is ignored.
6. **User Clicks "Run":**
   * In `App.jsx` (Lines 142–159):
     ```javascript
     useEffect(() => {
       if (!isRunning) return;
       const interval = setInterval(() => {
         handleStep();
       }, speed);
       return () => clearInterval(interval);
     }, [isRunning, handleStep, speed]);
     ```

## 14. Root-Cause Analysis — Registers and Memory Remaining Zero

```text
User loads program ──▶ Clicks Assemble & Load ──▶ Clicks Step / Run
                                │
                                ▼
                   Frontend App.jsx Line 128
          setClientSim(prev => simulateStep(prev, assembledProgram))
                                │
           ┌────────────────────┴────────────────────┐
           ▼                                         ▼
   [Client Simulator]                      [Backend RTL Simulator]
Updates in-memory JavaScript Uint32Array   Hardware executes in WSL2!
Registers write ONLY at cycle 5 (WB)      Registers write to RTL regfile!
           │                                         │
           ▼                                         ▼
Rendered on screen:                       `simulationService.step()` called
RegisterFileInspector displays:           BUT RETURN VALUE DISCARDED!
clientSim.registers (JS memory)           `/api/simulator/registers` NEVER CALLED!
           │                                         │
           ▼                                         ▼
   RESULT: ZERO VALUES!                     RESULT: ORPHANED IN WSL!
```

### Synthesis:
1. **The frontend does not display RTL data:** The React app displays `clientSim.registers` and `clientSim.memory`. It does not consume the hardware simulator state.
2. **In-flight pipeline latency:** In a 5-stage pipeline, an instruction fetched at Cycle 1 does not reach the Writeback (WB) stage until Cycle 5. In `simulatorEngine.js`, registers are only written when an instruction is in `next.pipeline.WB`. If fewer than 5 cycles have been stepped, registers are strictly zero.
3. **Empty program bug:** If the user steps before clicking "Assemble & Load", `assembledProgram` is empty (`[]`). Every cycle fetches NOP (`0x00000013`), so registers remain zero forever.

## 15. Root-Cause Analysis — Only Clock Appearing in Waveforms

1. **Active Tab Default:** When the user navigates to the Waveforms tab, `WaveformStudio.jsx` defaults to `'live'` mode (Live Logic Analyzer).
2. **Telemetry Source:** The Live Logic Analyzer renders signals from `clientSim.waveforms`, which is appended by `simulateStep()` in `frontend/src/services/simulatorEngine.js` (Lines 869–885).
3. **Inactive Signals:**
   * `clk` is calculated as `next.cycle % 2 === 0 ? 0 : 1`. This alternates every step.
   * `if_id_valid`, `id_ex_valid`, `ex_mem_valid`, `mem_wb_valid` depend on `next.pipeline.<STAGE>.valid`. When no instruction is in flight, all valid bits are `0`.
   * `stall`, `flush`, `fwdA`, `fwdB`, `alu_out`, `reg_write`, `mem_read`, `mem_write` are all `0`.
   * `pc` remains `0x0000`.
4. **Visual Result:** Every single signal track is drawn as a flat horizontal line at level 0, except for `CLK`, which toggles between 0 and 1. To the user, it appears that "only the clock signal is working."
5. **VCD Mode Separation:** Real hardware waveforms generated by Verilator are stored in `pipeline.vcd` and only viewable when the user switches to the 'vcd' tab and clicks "Stop Trace".
